01 · The big idea

What is an agent?

An agent is an app, built on a language model (an LLM), that can use tools to get things done.

In 2022, a chatbot was simple. Your message went straight to the language model, and its reply came straight back. The model could only use what it learned during training.

Now the model can reach the real world. Ask "What's in this PDF?" and it can use a search tool (that's RAG). Ask it to send an email, and it can use a send-email function. Want today's news? It uses a news tool. A model with tools like this is an agent.

◷ Before: plain chatbot

You → app → LLM → app → You

Reply limited to training data. No actions, no fresh facts.

✦ Now: an agent

You → app → LLM → tool call → run tool → LLM → You

Can fetch live data and take real actions.

Definitions vary. "Agent" is a new word, but a safe one is: an app, built on a language model, that can use tools.
02 · How it really works

How tool calling works

The most important idea: the model picks a tool, but your app runs it. The model never runs the tool itself.

Watch it build up, one step per click. The model sends a tool call (just a request). Your code runs the function and sends the result back. Only then does the model write the final answer.

Step 0 / 5
user"What's the temperature in São Paulo?" you see this
assistanttool_call → get_temperature(city="São Paulo") internal
your appruns the Python function → returns "26"
tooltool result fed back to the model: 26 internal
assistant"It's about 26°C in São Paulo right now." you see this
 
03 · Tools are ordinary functions

A tool is just a function

A tool is just a function. You can write it in any language; here it's Python.

This example returns a fixed number. A real tool could call a weather API, send an email, look something up in a database, or download a file: anything a function can do.

With power comes care. A tool that sends an email or changes a file affects real people. Well-built agents check with a person before doing anything important (see section 09).
# A tool = a function that does one job
FUNCTION get_temperature(city):
    IF city is "San Francisco" RETURN "72"
    IF city is "Paris"         RETURN "75"
    IF city is "Tokyo"         RETURN "73"
    RETURN "unknown / 70"
def get_temperature(city: str) -> str:
    # mock data (swap in a real weather API here)
    temps = {"San Francisco": "72", "Paris": "75", "Tokyo": "73"}
    return temps.get(city, "unknown / 70")
04 · Describing tools to the model

Tool schemas

The model can't see your code. So you give it a schema, a short description of each tool: its name, what it does, and what inputs it takes.

The descriptions matter a lot. They tell the model exactly what to put in each input, so better descriptions mean better tool calls. You can write the schema by hand, or let Pydantic build it for you.

get_temperature_schema = {
    "type": "function",
    "function": {
        "name": "get_temperature",
        "description": "Get the current temperature for a given city.",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "The city to get the temperature for. "
                                   "Add only the city name, not the state or country."
                }
            },
            "required": ["city"]
        }
    }
}
from pydantic import BaseModel, Field

class GetTemperature(BaseModel):
    city: str = Field(
        description="The city to get the temperature for. "
                    "Add only the city name, not the state or country."
    )

# Generate the same JSON schema, with far less clutter
params_schema = GetTemperature.model_json_schema()
Pass your tools with tools=[...] and tool_choice="auto". That lets the model decide when to use them.
05 · The conversation is a list

Messages & memory

An agent's memory is a list of messages. It is not the same as the chat the user sees on screen.

This inside list also holds the system prompt, the model's tool calls, and the tool results. Every message has a role:

system     # instructions: "You are a helpful assistant that…"
user       # what the person typed
assistant  # the model's reply: text OR a tool call
tool       # the result your app sends back (tagged with a call id)

So one question and answer on screen can be four messages inside: user → assistant (tool call) → tool (result) → assistant (final answer). The user only sees the first and the last.

06 · The heart of the agent

The agent loop

Keep calling the model until it stops asking for tools. That's the whole idea.

FUNCTION execute():
    LOOP forever:
        response = ask the LLM with (messages + tools)
        IF response has no tool calls:
            RETURN response text          # final answer
        add the tool-call message to messages
        FOR each tool_call:
            fn   = look up the function by its name
            args = the arguments the model chose
            out  = run fn(args)               # WE execute, not the LLM
            add a "tool" message with out (tagged with the call id)
import json

def execute(self):
    while True:
        response = self.client.chat.completions.create(
            messages=self.messages,
            tools=self.tools,
            tool_choice="auto",
        )
        choice = response.choices[0].message
        tool_calls = choice.tool_calls

        if not tool_calls:
            return choice.content          # final answer

        self.messages.append(choice)         # record the tool-call message
        for call in tool_calls:
            name = call.function.name
            args = json.loads(call.function.arguments)
            fn   = globals()[name]            # dynamic lookup by name
            result = fn(**args)               # your app runs the tool
            self.messages.append({
                "role": "tool",
                "tool_call_id": call.id,     # match the id back
                "content": str(result),
            })
Why the matching id? When you send a tool result back, you label it with the same tool_call_id the model used. That links each request to its answer, so the model doesn't get confused.
07 · Putting it together

The Agent class

Three methods: __init__ (set up), __call__ (handle a message), and execute (the loop above).

CLASS MyAgent:
    ON init(client, system, tools):
        store client, tools
        messages = empty list
        IF system: add system message to messages

    ON call(message):
        add user message to messages
        answer = execute()                # run the loop
        add assistant answer to messages
        RETURN answer

    execute(): ...                        # the loop from section 06
from huggingface_hub import InferenceClient
import os, json

class MyAgent:
    def __init__(self, client, system="", tools=None):
        self.client   = client
        self.system   = system
        self.tools    = tools or []
        self.messages = []
        if system:
            self.messages.append({"role": "system", "content": system})

    def __call__(self, message=None):
        if message:
            self.messages.append({"role": "user", "content": message})
        result = self.execute()              # the loop from section 06
        self.messages.append({"role": "assistant", "content": result})
        return result

    # def execute(self): ...  (see section 06)
# 1) a client (uses a token, not a raw API key)
client = InferenceClient(
    model="moonshotai/Kimi-K2-Thinking",   # must support function calling
    token=os.environ["HF_TOKEN"],
)

# 2) build the agent with a system prompt + tools
agent = MyAgent(
    client=client,
    system="You are a helpful assistant that can retrieve the temperature in a given city.",
    tools=[get_temperature_schema],
)

# 3) ask it something, globally!
print(agent("What is the temperature in Cairo?"))
# → "The current temperature in Cairo is …"

09 · Using AI responsibly

Building agents responsibly

An agent can take real actions: send messages, read data, change files. That power needs care. Here are everyday examples of doing it the right way.

Ask before acting

A study agent can email your teacher about a missed class.
Do this: it writes the draft and waits for you to tap "Send"; it never emails on its own.

Be honest it's an AI

A homework helper answers questions in a chat.
Do this: it says it's an AI that can make mistakes, and reminds you to check important answers.

Respect privacy

A library agent can search the school catalogue.
Do this: it looks up which books exist, but never reads other students' private borrowing records.

Show your sources

A research agent uses a search tool to answer a question.
Do this: it links where each fact came from, so you can check it and catch mistakes.

Set clear limits

A shopping agent can find products online.
Do this: it can suggest what to buy, but cannot spend real money without a person's approval.

Never deceive or harm

An agent could write messages that look like they're from someone else.
Do this: it never pretends to be a real person, helps you cheat, or spreads false information.
The big idea: keep a person in control. The more an agent can do, the more it should pause, explain, and ask before it acts.

11 · Reality check

This is for learning, not for real apps

The goal was to show how an agent works inside, not to build something ready to ship.

A real agent needs more: error handling (tools fail, the model sends bad inputs, the network drops), a limit on how many loop turns can run, checks on the tool inputs, logging, and safety checks before it takes actions. Real frameworks add all of this for you.

Once you understand the loop, these frameworks make a lot more sense:

smolagents
Hugging Face's lightweight agent framework.
LangChain
Popular toolkit for chaining LLM calls and tools.
LlamaIndex
Strong for RAG: connecting models to your data.
@tool decorators
Generate schemas automatically from a function.

Glossary

agent
An app, built on a language model, that can use tools.
tool call
The model's request to run a function with specific arguments.
schema
A structured description of a tool: name, purpose, parameters.
tool_choice="auto"
Lets the model decide when to call a tool.
system prompt
Hidden instructions that shape how the agent behaves.
RAG
Retrieval-Augmented Generation: a tool fetches data the model then uses.
